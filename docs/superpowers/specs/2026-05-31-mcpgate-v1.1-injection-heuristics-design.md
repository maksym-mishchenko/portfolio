# mcpgate v1.1 — Prompt-injection / tool-poisoning heuristics

> **Status:** Approved design — ready for implementation planning.
> **Implements:** Roadmap item *v1.1 — Prompt-injection / tool-poisoning heuristics*
> (`docs/superpowers/plans/2026-05-30-mcpgate-roadmap.md`).
> **Repo:** `github.com/maksym-mishchenko/mcpgate` (Go single binary).

## Goal

Detect known prompt-injection and tool-poisoning signatures in MCP traffic in **both
directions**, surface them as **non-blocking `WARN` annotations** layered on top of the
existing policy verdict, with **opt-in** escalation to `DENY`.

This closes the "Phase 3 heuristics" item from the security critique while respecting the
Coder critique ("fuzz / custom patterns are attack surface") by shipping a curated,
compiled-in signature set rather than a user-supplied regex loader.

## Key design decisions

1. **WARN is an orthogonal annotation, not a verdict.** A heuristic hit is independent of
   the policy decision: a call can be policy-`ALLOW` *and* heuristic-suspicious at the same
   time. The policy engine (`Evaluate`) is **untouched**. Warnings are carried alongside the
   verdict, never merged into the `Verdict` enum.
2. **Both scan directions.** Outbound (agent → server) tool-call args and `prompts/get`
   params, **and** inbound (server → agent) `resources/read` results and
   `sampling/createMessage` content. The inbound path is the tool-poisoning vector and the
   higher-value threat.
3. **Built-in signature set + a single global toggle.** A curated, versioned pattern library
   compiled into the binary. No per-server config and no user-supplied custom patterns in
   v1.1 (deliberately deferred — custom regex is attack surface).

## Architecture

### Unit 1 — `internal/scanner` (new package, pure, no dependencies)

```go
package scanner

// SignatureSetVersion identifies the compiled pattern library so audit rows
// record which version produced a match.
const SignatureSetVersion = "1"

// Threat is a single heuristic match.
type Threat struct {
    ID       string `json:"id"`       // stable signature id, e.g. "injection.ignore-previous"
    Severity string `json:"severity"` // "low" | "medium" | "high"
    Snippet  string `json:"snippet"`  // matched substring, truncated to maxSnippet chars
}

// Scan runs the compiled signature set over text and returns zero or more matches.
// Pure and panic-free: no I/O, no error path.
func Scan(text string) []Threat
```

- Built-in signatures (precompiled `regexp.Regexp` with an `ID` + `Severity`):
  - `injection.ignore-previous` — "ignore (all )?previous instructions" and close variants.
  - `injection.jailbreak` — common jailbreak fragments (e.g. "developer mode", "DAN",
    "you are now").
  - `exfil.base64` — `base64(` / long base64 blobs adjacent to exfil verbs.
  - `exfil.data-uri` — `data:` URIs carrying credential-like content.
  - `exfil.credential` — patterns resembling leaked secrets being moved (e.g. `AKIA`,
    `-----BEGIN ... PRIVATE KEY-----`, `Bearer ` tokens) in transit content.
- `Snippet` is truncated to `maxSnippet` (80 chars) so a giant matched payload can't bloat
  an audit row.
- The package is `Scan` + the signature table — exhaustively table-testable.

### Unit 2 — Config surface

New top-level `heuristics` block on `policy.Config`:

```yaml
heuristics:
  enabled: true          # default true; WARN-only behaviour is safe by default
  block_on_warn: false   # opt-in: escalate an otherwise-ALLOW call to DENY on any match
```

```go
type HeuristicsConfig struct {
    Enabled     bool `yaml:"enabled"`
    BlockOnWarn bool `yaml:"block_on_warn"`
}
```

- `enabled` defaults to **true**. Because WARN is non-blocking, defaulting on is safe and
  gives out-of-box value.
- This block lives on `Config` and is **read by the proxy**, not by `Evaluate`. The policy
  engine stays orthogonal.

> **YAML default note:** Go's `bool` zero value is `false`, so a missing `heuristics` block
> would yield `enabled:false`. The config loader must apply an explicit default of
> `enabled:true` when the `heuristics` key is absent, while still honouring an explicit
> `enabled:false`. Use a pointer (`*bool`) or a post-load defaulting step — the plan picks
> one; the requirement is: absent → on, explicit false → off.

### Unit 3 — Proxy integration (orthogonal flag)

The proxy computes the policy verdict exactly as today, then — when `heuristics.enabled` —
scans the relevant content and attaches any matches to the audit entry.

**Outbound gate** (existing `handleCall` path, `tools/call` args + `prompts/get` params):
1. `verdict := policy.Evaluate(...)` (unchanged).
2. If `enabled`: `warnings := scanner.Scan(stringifyArgs(args))`.
3. Attach `warnings` to the audit entry.

**Inbound path** (`recvServerResponse` / response relay for `resources/read` results and
`sampling/createMessage` content):
1. After receiving server content destined for the agent, if `enabled`:
   `warnings := scanner.Scan(content)`.
2. Attach `warnings` to that frame's audit entry.

**Combination rule (escalation only ever tightens):**

| Policy verdict | matches & `block_on_warn:false` | matches & `block_on_warn:true` |
|----------------|---------------------------------|--------------------------------|
| `ALLOW`        | `ALLOW` + warnings audited      | **`DENY`** + warnings audited  |
| `DENY`         | `DENY` + warnings audited       | `DENY` + warnings audited      |
| `ASK`          | `ASK` + warnings audited        | `ASK` + warnings audited       |

`DENY` and `ASK` are **never** downgraded. `block_on_warn` only ever *adds* denials.

### Data flow / audit

- `audit.Entry` gains `Warnings []scanner.Threat` (JSON-serialized).
- The `Warnings` field is **part of the HMAC-signed row** so warnings are tamper-evident like
  every other audit field. The hash-chain input must include the serialized warnings.
- `Notifier.Broadcast("audit", entry)` already ships the full entry → the browser dashboard
  receives warnings with no extra plumbing. Add a ⚠ badge on entries with non-empty
  `Warnings`, showing the matched signature `ID`(s) on hover/expand.

## Error handling / safety

- The scanner is pure and panic-free; a regex can never block or crash the proxy. There is no
  I/O and therefore no error path.
- WARN is non-blocking by design. With `block_on_warn:false`, heuristics can only *annotate* —
  they can never deny a call, so a false positive degrades to noise, not an outage.
- With `block_on_warn:true`, heuristics can only *add* denials (escalate ALLOW→DENY). They can
  never cause a `DENY`/`ASK` to be allowed. This preserves the gateway's fail-closed posture.
- Snippets are truncated to 80 chars to bound audit-row size.

## Testing strategy

**`internal/scanner` (table tests):**
- One positive case per signature (a string that must match, asserting the right `ID`).
- Negative / false-positive guard cases (benign strings that must **not** match), since
  false-positive rate is the named risk.
- Snippet truncation: an oversized match yields an ≤80-char snippet.

**`internal/proxy`:**
- Outbound match → policy `ALLOW`, audit entry carries the warning, call still forwarded.
- Inbound poisoning → `resources/read` / sampling response carries the warning on its audit
  entry, content still relayed (with `block_on_warn:false`).
- `block_on_warn:true`: an `ALLOW` call with a match is escalated to `DENY` (call not
  forwarded, `-32001` returned); a `DENY` stays `DENY`; an `ASK` stays `ASK`.
- `enabled:false`: no scanning, no warnings, no escalation regardless of `block_on_warn`.

**`internal/audit`:**
- A row with non-empty `Warnings` survives the HMAC chain round-trip and `VerifyChain()`
  passes; tampering with a warning field breaks verification.

**Config loader:**
- Absent `heuristics` block → `enabled:true`.
- Explicit `enabled:false` → off.

## Out of scope (deferred)

- Per-server heuristic overrides.
- User-supplied / external custom pattern files (attack surface; revisit only with strong
  demand).
- ML / model-based detection. v1.1 is deterministic pattern matching only.
- Auto-tuning or feedback-driven false-positive suppression.
